Follow the [runtime contract](../references/runtime.md). This playbook supplies a workflow, not additional tools or authorization.

When candidate review is required, use the existing [Review playbook](review.md) and its linked reviewer contract. The workflow here does not replace those review gates.

# Shipping

Land only the authorized, independently verified contiguous run from the bottom of a dependency chain. This route means PR landing; deployment or release remains a separately scoped action with its own evidence.

1. Establish specific existing landing authority: repository, PRs or queue, permitted merge mode, and excluded human-owned items. A plan, green CI, request to get merge-ready, or earlier PR creation is not that authority. Preserve authorization already granted; do not ask again. Inspect actual forge capabilities and merge semantics, then use one sufficient connector or supported CLI consistently.
2. Inventory the dependency chain from current remote PR bases and heads, not title order. For each PR record current head/base, parent, independent verifier, evidence, required checks and approvals, and mergeability. Independent review and real user/caller-surface acceptance must cover the behavior that would land. CI and approving bots are inputs, not substitutes. If independent runtime execution is unavailable, mark it pending and prepare only the work that can be proved.
3. Walk from the lowest unmerged item and stop at the first missing authority, verification, approval, conflict resolution, or required check. Freeze that contiguous run and its ceiling before landing. A verified item above a blocked dependency waits. Moving an actually independent item to trunk requires topology authority and fresh evidence against that base.
4. Reconcile evidence with the exact candidate and current trunk. Check source, dirty files, tests, dependencies, config, generated artifacts, callers, and runtime inputs. A patch ID or SHA alone cannot preserve verification. Unchanged patches can retain particular lane evidence only when the lane's affected inputs remain equivalent. For changed tests/docs/config, rerun the changed checks and review those changes. Build equivalence requires compared actual outputs with identified reproducible noise, not a guessed equivalence; a dev-server lane with no comparable output needs rerun when its inputs drift.
5. Test the merge result or rebase and reverify when trunk changes overlapping code, relevant callers or dependencies, or the checks that run. A lockfile-only overlap can avoid rebase only with a successful frozen install of the merge result and evidence that affected package resolutions match the verified head. Conflicts or failed install require repair and renewed checks; preserve the original failure evidence.
6. Freeze other branch/base writers while landing. One topology owner lands the lowest eligible PR at a time, confirming its base is trunk and its head is the one authorized and verified. Inspect tool semantics that could merge additional PRs implicitly. Do not arm auto-merge unless separately covered by the grant and protected against unverified head movement.
7. Read the remote result after each operation. Queued or auto-merge requested is not merged. Confirm the PR is actually merged into trunk and inspect the resulting trunk state. Only then may the topology owner perform authorized post-parent retarget/rebase of the next child onto the actual merge result. Use a checked remote lease for authorized history rewriting; unexpected remote writes stop mutation. Reconcile that child's evidence and required checks before its turn.
8. Stop at the frozen ceiling or the first new evidence gap. A stall earns diagnosis before mutation. Extending the run, changing a fix during landing, or adding another PR requires a newly scoped pass through the gates. Report remaining authorized ongoing work without silently declaring it complete.

Report the verified run and ceiling, per-PR verifier and evidence, actual merged states and how confirmed, queued items separately, and the next unresolved gate. No external verdict posts or discussion messages are implied by this playbook.
