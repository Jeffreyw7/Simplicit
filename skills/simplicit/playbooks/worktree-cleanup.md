When candidate review is required, use the existing [Review playbook](review.md) and its linked reviewer contract. The workflow here does not replace those review gates.

# Worktree cleanup

Inventory first and remove only specifically authorized, proven-disposable worktrees. Classification is advice, not permission. Dirty, untracked, ignored, unmerged, pinned, and active work can be unique user state.

1. Snapshot available disk space with supported platform tooling and inventory paths from `git worktree list --porcelain`; do not construct a guessed worktree path. Resolve each listed path and record branch, head, actual PR/base/merge state, tracked changes, all untracked and ignored paths, size, and known owner/use. Distinguish disposable generated artifacts from user data with evidence, not an ignore rule alone. Read repository instructions before touching `.git` metadata. Use an existing safe audit helper if available; no Bash/macOS helper is required.
2. Check actual merge ancestry against the relevant PR base, not an assumed main branch. Squash/rebase merges can require patch/content comparison and remote PR evidence, because ancestry alone may not establish whether unique work remains. A closed PR is not automatically merged. Record recoverable branch refs and commits before removal; a clean working tree can still hold unique unmerged commits.
3. Cross-check pinned or active user sessions and actual workers, processes, and nested tasks where available. A parent chat may own a sibling worktree through a helper. Missing transcript/sidebar visibility is uncertainty, not proof of inactivity. Active or pinned ownership holds the candidate even if its age/merge classifier says safe.
4. Produce a concrete candidate/held list. For every proposed removal name the exact resolved path, head/branch, unique-work assessment, dirty/untracked/ignored files, use evidence, and authorization covering that deletion. A cleanup inventory request stays read-only. An explicit cleanup grant may cover confirmed clean, merged, inactive candidates; it does not silently dispose of unknown files or unique work.
5. Hold anything with uncommitted edits, untracked/ignored files of uncertain value, unique unmerged commits, active ownership, unknown usage, or inadequate permission. Prepare a concrete preservation or recovery option before asking for a decision. Do not label untracked scratch disposable from its filename or delete it because a branch ref survives.
6. Immediately before authorized removal, recheck path, current head, working state, and active owner to close the race with resumed work. Verify the resolved absolute target is within the explicitly named worktree/cleanup boundary and is neither the repository root nor an ancestor/symlink escape. Use `git worktree remove` without force for a confirmed clean candidate. A refusal is evidence to inspect, not a reason to add force.
7. Do not follow a failed remove with recursive filesystem deletion by default. Any residual deletion requires its own confirmed contents, exact authorized path, preservation decision, and current boundary check. On Windows use one shell end to end with literal paths and native file operations. Never pipe discovered paths into another shell's destructive command. Prune only stale worktree metadata after checking that no live worktree depends on it. Branch deletion is a separate action.
8. Re-list worktrees, inspect removed paths and surviving refs, and compare available space with the initial snapshot. Report actual reclaimed space, not the sum of guessed sizes. Simulators, IDE state, package caches, and other reclaimers are separate named cleanup scopes; do not broaden this task to them automatically.

Report before/after disk evidence, exact removals and confirmed recoverability, each held item and reason, unavailable usage evidence, and any residual metadata or paths.
