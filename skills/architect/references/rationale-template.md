# Rationale outline

Adapted from pstack. Fill the relevant items in the existing brief; omit boilerplate.

1. **Problem:** observable outcome, constraints, and the uncertainty that makes the shape matter.
2. **Usage:** realistic caller examples, including an important failure case. Derive types from the intended caller contract.
3. **Shape:** state owners, data structures, signatures, validation boundaries, and complexity hidden behind the interface.
4. **Alternatives:** for consequential uncertainty, name a structurally different approach and explain the tradeoff. If only one shape is viable, name the constraint that rules others out.
5. **Decision:** chosen base, accepted costs, and evidence. When an arena ran, identify useful pieces retained or rejected; agreement is not proof.
6. **Open risks:** unknowns that need investigation versus product choices requiring user input.
7. **Next step:** the first verifiable implementation increment, or a clear design-only stopping point.
